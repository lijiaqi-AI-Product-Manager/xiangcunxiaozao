# P2 第一批 · 点单闭环 · 交付说明

日期：2026-10-17 · 依据：21号 §阶段计划、23号 §二、24号裁决、25号 §二放行指令

P2 按「分批交付」拆成三批，本批是**点单闭环**：顾客点单 → 下单 → 取餐号 → 老板实时收单 → 推进状态 → 顾客看到结果 → 再来一单。

## 二、这一批自己找出的问题（10 条）

**测试中发现、已修好的（3 条）**

1. **连点「+」只记一份**：写完代码、还没运行时就发现，两下点击读到的是同一个旧数量，都会发「数量 = 1」。改成请求排队、每次基于服务器最新数量再加减。
2. **「已把上一单加入购物车」的提示被购物车条挡住**：看截图 13 才发现，自动测试本身是通过的。已把提示移到购物车条上方。
3. **老板端等待时长不跟着订单变**：订单都做完了，面板还显示「前面 1 单、约 16 分钟」。原因是它只每 30 秒刷新一次；改成订单一有变化就刷新，并加了自动断言。

**需要老板定的（4 条）**

4. **营业日在午夜切换**：如果晚上营业过 0 点，0 点以后的单会从 001 重新编号，同一晚会出现两个 001。需要老板给一个营业日分界点（比如凌晨 4 点）。
5. **「每单平均 8 分钟」是我暂定的默认值**：参照的是十问十答第 4 问「现炒要等十几分钟」。老板端可以随时改。目前公式不区分菜的难易，一碗米饭和一条烤鱼算同样时间。
6. **一机一车的副作用**：同桌两个人各用自己手机点，后厨会收到两张单。这符合 24号 #8，但要提前告诉店员。
7. **顾客的订单记录只存在这台手机上**：清了浏览器数据就找不回历史单。会员登录后查全部历史，在下一批做。

**体验上还不够好、计划在后面的批次处理（3 条）**

8. **取消订单用的是浏览器自带的输入弹窗**：电脑上能用，平板上又丑又小，第三批换成页面内的输入框。
9. **断线重连只验证了正常情况**：长时间断网后恢复、服务器重启这类情况还没专门测，第三批补。
10. **老板端每次刷新页面都要重新点「开始接单」**：这是浏览器的规定，绕不开。按钮写得很显眼，但需要店员养成习惯。

## 三、P2 剩下的两批

- **第二批 · 会员与储值**：会员号 + 4 位密码登录（连错锁定）、余额与流水查询、储值支付（下单即扣、取消自动冲销）、老板端充值 / 调整 / 流水 / 打单、每晚自动对账。
- **第三批 · 菜品管理与营业**：上下架、改价、图片上传（四项防崩）；营业时间与打烊停止接单；取消原因改为页面内输入；断线等异常场景补测。

## 四、怎么自己跑一遍

```bash
npm run e2e
```

跑完后看 `docs/screenshots/p2-batch1/` 里的 13 张图。手动体验：依次运行 `npm run dev:server`、`npm run dev:customer`、`npm run dev:admin`，然后打开顾客端 http://localhost:5173/?table=12 和老板端 http://localhost:5174。老板密码在 `.env` 文件的 `ADMIN_PASSWORD` 一行，这个文件不进 git。
