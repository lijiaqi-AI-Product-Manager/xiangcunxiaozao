# 部署与回滚手册

> 写给下一个接手的人（也可能是几个月后的自己）。读完这一份，应该能把系统装到一台新服务器上、确认它在正常工作、出事时 10 分钟内退回上一版。
> 最后核对：2026-10-18，对应 main 上的标签 `p5-closeout`。

## 第一章 · 现状部署架构（先说清楚「现在是什么样」）

### 1.1 一句话结论

**新系统还没有上过生产。** 现在顾客在店里用的仍然是老系统；新系统只在开发电脑上跑过，配合自动测试和演示网页验收。所以 58号说的「三批合并上生产」，代码这一半已经做完（全部合入 main，每一步打了标签），**生产那一半要等服务器定下来才能做**——见 1.4 和第二章。

### 1.2 四个问题的答案

| 问题 | 现在的答案 | 依据 |
|---|---|---|
| 服务器在哪 | **还没有**。新系统只在开发电脑（Windows）上运行过 | `P1-交付说明.md` 第 53 行、`P2-总验收包.md` 第 85 行：服务器、域名、对象存储都还没定 |
| 怎么跑的 | 开发时三个进程：后端（Node + SQLite，端口 8787）、顾客端和老板端（Vite 开发服务器，5173 / 5174，把 `/api`、`/media` 转给后端） | `apps/server/src/main.ts`、`packages/ui-kit/src/vite-brand.ts` |
| 谁能操作 | 代码：仓库所有者（GitHub 私有仓库 `lijiaqimun-coder/xiangcunxiaozao`，推送见第五章）。老板端：知道 `ADMIN_PASSWORD` 的人 | `.env`（不进 git） |
| 依赖什么 | Node.js 22+（开发机是 24）；npm 11；数据库是一个 SQLite 文件；不依赖任何外部服务（没有支付、短信、第三方登录） | 根目录 `package.json`、`README.md` |

### 1.3 系统由什么组成

```
顾客手机 ──扫桌上二维码──▶ 顾客端网页（静态文件）──┐
                                                    ├─ /api/*、/media/* ─▶ 后端（Node，一个进程）─▶ data/app.db（SQLite，一个文件 = 整本账）
老板电脑 / 平板 ─────────▶ 老板端网页（静态文件）──┘                         └▶ data/uploads/（老板上传的菜品图）
                                                                                 └▶ backups/（每 10 分钟一份本地快照）
```

- **数据全在两个地方**：`data/app.db`（订单、会员、余额流水、菜品改动、设置）和 `data/uploads/`（菜品图）。备份、迁移、回滚都围绕这两样。
- 后端只提供接口，**不提供网页文件**。正式部署时网页文件（`npm run build` 生成的 `dist/`）要由前面一层网页服务器（推荐 Caddy）直接给出，并把 `/api`、`/media` 转给后端。

### 1.4 正式上线前必须先定的事（高斯 / 老板）

| # | 要定的 | 我的建议 | 为什么 |
|---|---|---|---|
| 1 | 服务器 | 一台最小规格的 Linux 云主机（1 核 1G 足够），机房选新加坡或吉隆坡 | 顾客在吉隆坡，近 = 快；整个后端一个进程、一个数据库文件，不需要大机器 |
| 2 | 域名 | 买一个短域名，二维码印这个地址 | 二维码一旦印到桌上就不好改；以后换服务器只改域名解析 |
| 3 | 对象存储（异地备份） | Cloudflare R2 或 Backblaze B2 开一个桶 | Litestream 把每次写入实时复制过去，服务器整台坏掉最多丢几秒数据；模板已写好（`deploy/litestream.yml`） |
| 4 | 谁有服务器登录权限 | 只给 1–2 个人，用密钥登录，不用密码 | 27号 #7：数据库文件里有全部余额，服务器登录 = 账本钥匙 |

## 第二章 · 部署步骤（服务器定了以后照做）

以 Ubuntu 24.04 为例，命令都在服务器上执行。`<域名>` 换成真实域名。

### 2.1 一次性准备

1. 装 Node.js 22 以上、git、Caddy（网页服务器，自动申请 HTTPS 证书）、Litestream。
2. 建一个专门跑服务的用户（比如 `app`），代码放在 `/srv/app`，数据库只给这个用户读写。
3. 拉代码：`git clone <仓库地址> /srv/app`，然后 `cd /srv/app && git checkout <要上线的标签>`。
4. 复制 `.env.example` 为 `.env`，填：`BRAND=xiangcun`、`DB_PATH=./data/app.db`、`BACKUP_DIR=./backups`、`UPLOAD_DIR=./data/uploads`、`API_PORT=8787`、`ADMIN_PASSWORD=`（老板自己设，至少 8 位，**不要写进聊天或任何文档**）。
5. `npm ci`（严格按 `package-lock.json` 装，和测试时的版本一模一样）。
6. `npm run check`（安全审计 + 产品化 + 色彩 + 数据 + 类型 + 单元测试，全过才继续）。
7. `npm run build -w @app/customer` 和 `npm run build -w @app/admin`，得到两个 `dist/`。
8. 后端设成开机自启的系统服务（systemd），启动命令：`npx tsx --env-file=.env apps/server/src/main.ts`，工作目录 `/srv/app`，失败自动重启。
9. Caddy 配置两个站点：顾客端 `<域名>` → `apps/customer/dist`，老板端（建议单独子域名，如 `boss.<域名>`）→ `apps/admin/dist`；两个站点都把 `/api/*`、`/media/*` 转给 `127.0.0.1:8787`。老板端的 `/api/admin/stream` 是实时推送（SSE），Caddy 默认支持，不要开响应缓冲。
10. Litestream：按 `deploy/litestream.yml` 里的注释填三个变量，`path` 改成 `/srv/app/data/app.db`，设成系统服务。`data/uploads/` 另外每天同步一次到同一个桶（图片不在数据库里，P2-批3 自查 #9）。
11. 老板端登录 → 「门店信息」填地址 / 电话 / 营业时间 / WhatsApp；「菜品管理」配今日招牌；「实时订单」设营业时间。

### 2.2 每次发版（一个打烊窗口内完成）

1. **打回滚锚点**：在服务器上 `git tag -a deploy-YYYYMMDD-before -m "发版前"`（记下当前运行的是哪个提交）。
2. **先备份**：`npm run backup`（立刻做一份快照），确认 `backups/` 里多了一个文件。
3. `git fetch && git checkout <新标签>`，`npm ci`，`npm run check`，两个前端 `build`。
4. 重启后端服务。
5. 走第三章的验证清单，三张全部打勾才算发版完成。
6. 在本手册末尾「发版记录」加一行：日期、标签、谁做的、验证结果。

> 数据库结构从 P2 到现在**没有变过**（`apps/server/migrations/` 五个文件一个都没改），58号收尾这批新加的东西（今日招牌、门店信息）都存在已有的 `settings` 表里。所以这次上线和回滚都**不需要动数据库**。以后如果新增迁移文件，回滚前必须先读第四章 4.3。

## 第四章 · 回滚（目标 10 分钟内）

### 4.1 什么时候回滚

验证清单任何一项不过、且 5 分钟内找不到原因；或者营业中出现顾客无法下单、老板收不到单。**先回滚恢复营业，再慢慢查原因。**

### 4.2 步骤

1. `cd /srv/app && git checkout <上一个好的标签>`（发版前打的 `deploy-YYYYMMDD-before`，或 main 上的 `p4-b3` 这类批次标签）
2. `npm ci`
3. 两个前端 `build`
4. 重启后端服务
5. 走一遍清单二的「结算 → 出号」和清单三的「收到单」两项

2026-10-18 在开发机上演练过一次（从现在的 main 退回 `p4-b3`，全新目录）：拉代码 + 切标签 22 秒、`npm ci` 12 秒、两个前端构建 4 秒，合计 38 秒。服务器网速慢一些也只是多几十秒；加上重启和两项验证，10 分钟目标很宽裕。

### 4.3 数据要不要回滚

**一般不要。** 回滚只换代码，`data/app.db` 原样留着——营业中产生的订单、充值都在里面，回滚数据库会把它们一起丢掉。只有确认新版本**写坏了数据**时才恢复备份：停后端 → 把 `data/app.db` 换成 `backups/` 里出事前的那份（或用 Litestream 恢复到指定时间点）→ 启动 → 用老板端「会员管理 → 立即对账」确认余额和流水一致。

### 4.4 main 上现成的回滚锚点

| 标签 | 是什么 |
|---|---|
| `pre-58-main` | 58号合并前的 main（P2 基线） |
| `p3-done` | 合入 P3 之后 |
| `p4-b1` / `p4-b2` / `p4-b3` | 54号三批依次合入之后 |
| `p4-b4` | 56号（会员黑金、菜名一行、双环章）合入之后 |
| `p5-closeout` | 58号收尾（安全批、门店信息、演示版、文档）合入之后 = 现在 |

## 第五章 · 常见故障

| 现象 | 先看哪里 | 通常的原因和处理 |
|---|---|---|
| 顾客端整页「暂时连不上服务器」 | `/api/health` 能不能打开 | 后端没起来：看服务日志；`.env` 缺变量时启动日志会直接写「缺少环境变量 XXX」 |
| 老板端一直「连接中断，正在自动重连」 | Caddy 配置 | 实时推送被缓冲或超时：老板端 40 秒没心跳会自动重连并补上断网期间的单；持续断开就检查反向代理 |
| 老板端登录提示「密码错误次数过多，已锁定」 | 等提示里写的分钟数 | 防暴力猜密码的锁定，到时间自动解开；忘了密码只能在服务器上改 `.env` 再重启 |
| 上传图片失败「存储目录不可写」 | `data/uploads` 权限 | 目录要归服务用户所有 |
| 对账横幅变红「发现不一致」 | 老板端「会员管理」 | 余额和流水合计对不上：**停止充值**，导出流水，按横幅里的会员号逐个核对；不要直接改数据库 |
| `npm run check` 第一步就失败 | 终端输出 | `check:audit` 发现了新漏洞（中危及以上）：按提示升级对应的包，跑全量测试后再发版 |
| 顾客说菜价不对 | 老板端「菜品管理」 | 后台改价只影响之后的新单；老订单按下单时的价格记账，这是故意的 |
