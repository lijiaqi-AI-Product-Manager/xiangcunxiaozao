## 二、对账结论（详表见 [P3-菜单对账表.md](P3-菜单对账表.md)）

打个比方：把 11号清单当进货单，把菜单数据当仓库，一行一行对。

1. **11号清单编号行是 99 行，不是 96**。按十一个分区逐行数：L8 + S12 + M6 + XL3 + 罐装3 + A8 + B14 + C18 + D12 + E13 + V2 = 99。99 行全部在数据里找到，菜名和价格都对得上。
2. **B 级 41 比 A+B+C 40 多出的 1 道 = C11 外婆菜炒肉末**（内部ID c11b）。它不在 11号清单里，是 22号 #9 裁决保留、24号拆成 C11a/C11b 的那一道。账是平的，不是漏数。
3. **「86 道」是 11号末尾统计脚注里的估算**（原文「菜品约 86 道」），不是逐行数出来的数。我把「去掉整个分区正好剩 86」的组合都算了一遍，共 5 种，比如去掉整个店长推荐区，没有一种说得通。所以这 13 道差额没有对应的具体菜，数据也没有少收。
4. 数据总共 104 条 = 99 行编号菜 + 1 道清单外保留 + 4 条主食/配送费；顾客能点的 102 项（两条配送费不上架）。
5. 对账表可以随时重跑：`npm run reconcile:menu`。以后菜单数据一变，表跟着变，不靠手抄。

## 四、背景水印（高斯意见）

- **原来**：每个字 276 像素高，四个字竖排 1104 像素，手机屏幕只有 812 像素，所以「湘」字头和「灶」字尾被切掉，右边也切掉一条。
- **现在**：字号按字数自动算，四个字合起来占屏幕可见高度的 88%，在 375×812 的手机上每个字约 179 像素。上下左右都完整显示，位置和透明度都没变，还是大字竖排靠右，"大大的背景"风格保留。
- 高度按「浏览器地址栏和工具栏都露出来时」的可见高度算，工具栏弹出来也不会切字。
- 自动测试会检查水印在手机屏里完整、不出界。

## 五、我自己发现的问题（6 条）

1. **"稍微小一点"做不到只小一点**：四个字要在屏幕里放全，每个字最大只能约 200 像素，所以最少要比原来小 35% 左右。现在是 179 像素，上下各留一点空。如果高斯觉得太小，可以：A. 保持现在（推荐）；B. 放大到占屏幕 96%，上下几乎贴边；C. 改成只显示两个字（比如「小灶」），每个字可以更大。
2. **导入时多收了一个假套餐「统计」**：11号末尾那行「统计：菜品约86道…」被当成一个套餐收进了数据。它没有在任何页面显示过，但数据里不该有。已修导入脚本，重新导入后只删掉了这一条，其余 104 道菜一个字没变，并加了测试防止再犯。
3. **菜单列表图片上出现了下划线**：上一批把列表里的菜图做成可点的链接，图上的占位文字（菜名、「实拍图上线中」）因此带上了下划线。这次看截图时发现的，已去掉。上一批提交时我把重跑出来的列表截图还原成了 P2 原版，所以交付的截图里没有暴露出来，这是我自查的漏洞。
4. **长截图里的水印偏大**：截长图时我把窗口拉成整页那么高，水印按窗口高度算字号，长图里就变得特别大，和真机不一样（上一批的长图也是这样）。现在截图前先把水印定在手机上的实际大小，长图里的水印和真机一致。
5. **老手机上水印可能变小**：「工具栏露出来时的可见高度」这个单位，iPhone 要 iOS 15.4 以上、安卓 Chrome 要 108 以上才认。更老的手机会退回系统默认字号，水印变成很小一行字，但不影响点单。在马来西亚这类老手机占比应该很小，先不处理，你觉得需要我再加一层兜底。
6. **P2 的部分截图跟着变了**：第三批截图 04（顾客端新价格新图片）里招牌跳跳蛙不再有测试图，测试图改到了下饭咸鸭蛋；两态截图里招牌跳跳蛙也回到原价 48、没有测试图。这是本次修复造成的正常变化，已经一起提交；其他 P2 截图只有像素级差异，保留原版没动。
