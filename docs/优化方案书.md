## 〇、先给结论

## 一、P0 紧急止血（开业前必修，7 项）

### P0-1 · 下单没有幂等键：网络一抖，订单丢了顾客不知道

**这是整份报告最重要的一条。**

**现象**：顾客点"提交订单"→ 服务端建单成功、取餐号已分配、厨房已打印 → 但响应在路上丢了 → 顾客看到"网络连接失败，请检查网络后重试" → 顾客再点一次 → 系统回"购物车是空的"。

**实测证据**：用浏览器拦截 `/api/order/submit` 的响应（第一次请求真实到达服务端，订单真的建了，但响应被丢弃，模拟弱网超时）：

```
提交按钮文本: 提交订单 · RM 48
请求次数: 1
页面上的报错文案: [ '网络连接失败，请检查网络后重试' ]
```

此时服务端**已经有一张新订单**。顾客再点一次，`[实测]` 用 curl 直接打同一购物车：

```
{"error":"business","message":"购物车是空的"}
```

**根因**（两处叠加）：

1. `[代码] apps/server/migrations/002_cart_orders.sql:31` — `orders` 表只有 `UNIQUE (business_date, pickup_no)`，**没有请求幂等键**。对比一下：储值流水有 `idempotency_key UNIQUE`、退款有 `request_key UNIQUE`，唯独最关键的"下单"没有。
2. `[代码] apps/server/src/orders.ts:92` — 下单事务最后一句 `DELETE FROM cart_items WHERE cart_id = ?` 把车清空了。所以重试必然撞上"购物车是空的"。
3. `[代码] packages/ui-kit/src/fetchJson.ts:7` — `await fetch(url, init)` **没有任何超时控制**，全文件没有 `AbortSignal`。这意味着请求可能永久挂起——按钮一直显示"提交中…"，顾客不知道该怎么办，只能刷新或重进。

**为什么顾客找不到自己的单**（这点也很关键）：
- `[代码] apps/customer/src/App.tsx:76` — 取餐页的设备号取的是 `cart.cart?.id`，**不是独立的设备 ID**。而 `afterSubmit()`（`api.ts:109`）是一个没被 await 的 `void` 调用，它去 refresh 一个已经被清空的购物车；如果这个 refresh 也失败了，`latest.current` 就停在旧值，取餐页拿不到有效 deviceId，直接卡在"加载中…"。
- `[代码] apps/customer/src/App.tsx:74` — 下单页面上**没有任何"我下过单了，查看我的订单"的出口**。

**修法**（三步，按顺序做）：

1. **加幂等键**（后端，约 0.5 天）
   - 迁移：`ALTER TABLE orders ADD COLUMN request_key TEXT;` + `CREATE UNIQUE INDEX orders_request_key ON orders(request_key) WHERE request_key IS NOT NULL;`
   - 前端 `submitOrder` 生成一次 `requestId`（`crypto.getRandomValues`，和现有退款用的是同一套写法），随 body 提交；**失败重试时复用同一个 requestId**。
   - `orders.submit()` 开头：如果 `request_key` 已存在，直接 `return this.get(已有订单id)`——和 `refund()` 现有的幂等写法完全一致，复制即可。
2. **给 fetchJson 加超时**（约 0.5 天）
   - 加 `signal: AbortSignal.timeout(15000)`（下单这类写操作可以放宽到 20 秒）。
   - 超时文案必须是"**提交超时，正在为你确认是否已下单…**"，而不是"网络失败"——因为这时订单很可能已经建了。
3. **下单失败后给出明确出口**（前端，约 0.5 天）
   - 错误卡片上加一个按钮：「我可能已经下过单了？查看我的订单 →」。
   - 顾客端引入独立的 `deviceId`（首次访问生成并持久化到 localStorage），不再依赖 cart.id；同时给 `orders` 表加 `device_id` 索引（已有 `orders_by_device`）。

**验证方式**：用同样的拦截手法重跑——第二次点提交，应该看到**同一张订单**（同一个取餐号），而不是"购物车是空的"。

### P0-2 · 跨营业日看板漏单：昨天的单从界面消失，取餐号还会撞号

**现象**：店开到晚上 23:59 跨到第二天 00:00，老板端订单台不刷新的话，新单直接"不出现"。更糟的是取餐号重新从 001 开始，界面上可能出现两个 001。

**根因**：

- `[代码] apps/admin/src/api.ts:80` — `es.addEventListener('hello', () => { ... void reload(); })`，`reload()` **只在连接建立和 hello 时跑一次**。之后全靠 SSE 增量推。跨日后 `business_date` 变了，但前端列表还是按旧的一天累积，而增量推的是新一天的单——两者混在一起，`pickup_no` 重复。
- `[代码] apps/server/src/app.ts:320` — `hello` 事件里带了 `{ day: orders.today() }`，**前端收到后完全没用这个字段**。设计时想到了，实现时漏了。

**修法**：
- 前端在 `order.created` 事件里比对事件的 `businessDate` 与当前列表的日期，不一致就 `reload()`。
- 或者更简单：`hello` 的时候记住 `day`，每次收到事件都比一次。
- 另外 SSE 每 25 秒有 `ping`，可以在 ping 里带上 `day`，前端比对一次即可（成本几乎为零）。

**工时**：0.5 天。

### P0-3 · 切到别的页面就收不到新单：新单不响铃、不提示

**现象**：老板在"菜品管理"页改价格，来了一单，**没有任何提示音、没有弹窗、左边"订单"菜单也没有红点**。等改完价格切回订单页，才发现已经堆了三单。

**根因**：

- `[代码] apps/admin/src/App.tsx:120` — `{key === 'orders' && <OrdersBoard />}`。这是**条件渲染**，切走时组件整个卸载，`useLiveOrders` 的 `useEffect` 清理函数执行，`es?.close()` 把 EventSource 关了。
- 提示音 `playChime()` 在 `OrdersBoard` 内部（`App.tsx:144`），组件不在就没人调用。

**修法**：
- 把 `useLiveOrders` 提升到 `App.tsx` 顶层（不受页签切换影响），把新单数和最后一张新单传给各页签。
- `OrdersBoard` 只负责渲染，不再自己订阅。
- 左侧菜单"订单"上加未读红点（和对账异常的红点同一个机制）。
- 提示音改在顶层调。

**工时**：1 天。**这条我很推荐做**——它直接决定"老板敢不敢离开订单页去干别的"。

### P0-4 · SSE 每 25 秒泄漏一个定时器

**现象**：老板端开一整天，内存缓慢增长；长时间连接后开始出现卡顿。

**根因**：

```ts
// [代码] apps/server/src/app.ts:327
await new Promise<void>((r) => { wake = r; setTimeout(r, 25000); });
```

`setTimeout` 的返回值没有保存，`stream.onAbort` 里只 `wake?.()` 唤醒 Promise，**没有 `clearTimeout`**。连接断开后，那个 25 秒的定时器仍然会到点执行一次，闭包里还持有 `stream` 对象。

一天 8 小时 × 老板端 1 个连接 = 1152 个定时器，每个 25 秒后自然释放。看着不多，但：
- 老板端可能开 2-3 个设备（前台 iPad + 后厨屏幕 + 老板手机）
- 每次 Wi-Fi 抖动重连都会留一个
- 累计下来是持续的内存和事件循环压力

**修法**：`const t = setTimeout(r, 25000); stream.onAbort(() => clearTimeout(t));` ——三行代码，5 分钟。

### P0-5 · 两台设备同时改单，后到的把先到的覆盖掉

**现象**：前台 iPad 上把这单从"新单"拖到"制作中"；同一时刻老板手机上点了"取消"。两个请求几乎同时到达，最终状态取决于谁后到——**没有任何冲突检测**。

**根因**：

- `[代码] apps/admin/src/api.ts:100` — `const replace = (o) => setOrders((list) => list.map((x) => (x.id === o.id ? o : x)))`，整条订单覆盖，不看版本。
- `[代码] apps/admin/src/App.tsx` 的 `order.updated` 事件处理也是同理。
- 后端 `setStatus()` 有状态流转校验（`NEXT_STATUS`），触发器也有 `orders_status_flow` 兜底——**这一层是安全的，不会出现非法状态**。问题在"两个都合法的操作谁赢"以及**前端显示的那个赢家可能是错的**（本地乐观更新 vs 服务端实际结果）。

**修法**：
- 后端 `setStatus` 已经返回了最终的 Order DTO，前端拿到后**以返回值覆盖本地**，不做乐观更新。
- 若要更严格：`orders` 加 `version INTEGER DEFAULT 0`，`UPDATE ... WHERE id = ? AND version = ?`，不匹配返回 409「这单刚被其他设备改过，已为你刷新」。

**工时**：0.5–1 天。

### P0-6 · 下单按钮的"提交中"提前消失

**现象**：顾客点提交后，页面**立刻**跳到取餐页（取餐号可能还没出来），如果服务端还在建单，取餐页先显示"还没有订单"，1–2 秒后才出现。

**根因**：

```ts
// [代码] apps/customer/src/Pages.tsx:52
onDone();
// [代码] apps/customer/src/App.tsx:74
onDone={() => { void cart.afterSubmit(); go('pickup'); }}
```

`afterSubmit()` 返回的 Promise 被 `void` 掉了，**没有 await**，直接 `go('pickup')`。取餐页此时拿到的 deviceId 是旧的购物车 ID，订单列表还没刷新。

**修法**：`onDone` 改成 async，`await cart.afterSubmit()` 之后再跳转；跳转前在按钮上保持"提交中…"（`sending` 状态目前会被 `finally` 提前置回 false，因为跳转和 setSending 是并行的）。

**工时**：0.5 天。这条和 P0-1 的修法是同一片代码，一起做最省事。

### P0-7 · `window.confirm` 在 iPad / WebView 上可能被静默忽略

**现象**：所有危险操作（退款、改价、删图、充值调整、暂停接单）都用 `window.confirm` 做二次确认：

```
[代码] apps/admin/src/App.tsx:334  暂停接单
[代码] apps/admin/src/Dishes.tsx:140  改价
[代码] apps/admin/src/Dishes.tsx:170  删除图片
[代码] apps/admin/src/Members.tsx:187  充值/调整
[代码] apps/admin/src/Refunds.tsx:37  退款
```

在 iPad Safari 的某些版本、以及被"添加到主屏幕"后的 WebView 模式下，`confirm()` 可能**直接返回 true 而不显示对话框**。也就是说：**二次确认等于没有**，老板手滑点一下退款就真退了。

**根因**：`window.confirm` 是同步阻塞的浏览器原生 API，移动端 Safari 对其支持一直不稳定，尤其是 PWA 模式。

**修法**：写一个 `<ConfirmDialog>`（项目里已经有 Dialog 组件用于购物车，`getByRole('dialog')` 能用），五处替换掉。**约 1 天**，但这是"钱的安全"。

## 二、P1 业务正确性（开业前尽量修完，9 项）

### P1-1 · 混付退款先退储值，柜台现金收不回来

**现象**：顾客用"储值 20 + 现金 28"付了 48 元。后来退了全部 48 元。系统把 20 元退回储值余额，剩下 28 元记"待柜台退还"。**看似合理**——但如果你退的是**一半**（24 元）：

```ts
// [代码] apps/server/src/orders.ts  refund()
const storedPart = Math.min(amount, Math.max(0, storedLeft));
```

**先退储值，退满了才退现金**。所以退 24 元 → 24 元全进储值余额，柜台现金一分不用给。顾客拿到的是"储值余额"，不是你手上的现金。他下次来消费才会用掉。**对你来说现金流没出去，但顾客会觉得"你说退钱，结果退的是券"**。

反过来，如果先退现金，你手上现金直接出去。**两种都不完美，但至少规则要明确并告知顾客。**

**修法**：改成"按比例退"或"先退现金后储值"，并在退款确认弹窗里**明确写出**"本次退储值 X 元、退现金 Y 元"。现在的弹窗只有金额合计。

**工时**：0.5 天（改算法）+ 0.5 天（改文案）。

### P1-2 · 等待时长口径不对，会把顾客吓跑

**现象**：店里 8 单未完成，每单平均 8 分钟，顾客看到"当前等待约 **72 分钟**"。实际可能只要 20 分钟。

**根因**：

```ts
// [代码] apps/server/src/orders.ts:257
const queue = this.db.prepare(`SELECT COUNT(*) FROM orders WHERE business_date = ? AND ${ACTIVE}`).pluck().get(this.today());
// ACTIVE = "status IN ('pending', 'cooking')"
return { minutes: (queue + 1) * this.minutesPerOrder(), queue, source: 'auto' };
```

公式本身没错（8 单未完成 × 8 分钟）。问题是**"每单平均分钟"这个参数是全局静态值**（`brand.wait.minutesPerOrder = 8`），不管店里几口锅、几个灶、几单是凉菜几单是炒菜，都按 8 分钟算。而且**没有考虑已经做了一半的单**——`cooking` 状态的单不应该算满 8 分钟。

**修法**（分两级）：
- **立刻能做**：`pending` 单算满 8 分钟，`cooking` 单算 4 分钟（一半）。公式：`pending*8 + cooking*4 + 8`。
- **更好**：老板端加一个"当前实际出餐速度"调整（已经有 `manualMinutes` 手动覆盖，但埋得深，老板不一定知道用）。

**工时**：0.5 天。**这条影响转化率**——顾客看到 72 分钟可能直接走了。

> 顺带说明：`etaMinutes`（订单进度页的预计时间）用的是 `ahead * minutesPerOrder`，`ahead` 是"排在前面还有几单"，这个口径**是对的**。只有首页那个"当前等待约"用错了。

### P1-4 · 打印健康检查只看端口通不通，缺纸也显示绿灯

**现象**：老板端"打印设置"页，打印机缺纸、离线、卡纸——只要 TCP 端口能连上，就显示"正常"。等到下单时才发现打不出来。

**根因**：

```ts
// [代码] apps/server/src/print/transport.ts  health()
// 只做 TCP connect 测试，不做 ESC/POS 状态查询（DLE EOT）
```

ESC/POS 标准里有 `DLE EOT n` 指令可以查打印机实时状态（缺纸、开盖、离线）。芯烨 XP-236B 支持。

**修法**：`health()` 里发 `DLE EOT 1` 和 `DLE EOT 4`，读回 1 字节状态位。**约 1 天**（要处理超时和不同固件的响应差异）。

### P2-6 · 无边车（加菜）概念 ✅ 已完成

顾客点了一桌，吃完了想再加两个菜。之前必须**重新下一单**——生成一个新的取餐号，最后结账要合并两张单，后厨也得多看一张票。

**做法：另开一张子单，钱各记各的，对外始终是一个取餐号。**

选这条路是因为一张单的 `total_sen` 在系统里是「下单那一刻的价」：退款按行退、账本只增不删、`order_items` 还有触发器禁止 UPDATE/DELETE（迁移 002，有意为之——已经下给后厨的菜不能被悄悄改掉）。如果让加菜往同一张单里追加行、改 `total_sen`，日结单、看板、退款分摊比例全都要重新定义「这张单当时是多少钱」，等于把已经稳定的账务推倒重来。

子单方案下这些口径**一个都不用改**，天然就是对的。

| 层面 | 做法 |
|---|---|
| 数据 | `orders` 加 `parent_order_id` / `added_at` / `add_seq`（迁移 012），`(parent_order_id, add_seq)` 唯一索引兜幂等，两个触发器禁止自指、禁止子单缺 `add_seq` |
| 取餐号 | 子单不占号，但 `(business_date, pickup_no)` 是表级唯一约束（SQLite 改不了），所以子单写一个「当天最大 + 1」的占位号，**接口层一律换成父单号**（`toDto` 的 `rootPickup`） |
| 顾客端 | 取餐页「还想加点什么？给 027 加菜」→ 点单页顶部常驻「正在给 027 号加菜 · 桌号 8 · 付款方式沿用原单」→ 购物车按钮变成「去加菜」→ 结算页标题「确认加菜」、**不再问桌号和付款方式**（这两件事顾客刚才已经决定过了，再问一遍只会多一个填错的入口，尤其是桌号，填错菜就送到隔壁桌） |
| 幂等 | `addDishes` 的 `requestId` 校验必须在**所有业务校验之前**：重试时购物车已被第一次成功清空，先查「购物车空不空」会得到 400 —— 顾客以为加菜失败，其实加成功了 |
| 老板端 | 子单单独进订单台，卡头打「加菜 +1」；父子两张卡都写「这一桌一共 RM 39.8（这张单 RM 19.9）」，收款按整桌收才不会少收 |
| 列表 | 顾客端两张列表都过 `rollUpAdditions()` 把子单收回父单，否则取餐页会拿到子单——号码对（换成了父单号）但 `addCount` / `groupTotalSen` 只算在父单上，页面会显示成「没加过菜、合计算少了」 |

三条业务规则（现场一定会遇到）：已取消的单不能加菜（那桌已经退了）、已完成的单不能加菜（吃完了再加就是新的一单）、加菜单再想加菜一律挂到最上面那张主单（否则会出 3 层 4 层，「这一桌一共多少钱」要递归算，极易算漏）。

**实拍验证**：完整走通「下单 029 → 加菜 → 201 → 回执『加菜成功·取餐号还是 029·这一桌现在一共 RM 39.80』→ 取餐页号不变、合计变 39.8、出现『这一桌已经加过 1 次菜』→ 老板端看到『加菜 +1』卡」，顾客端 6 张 + 老板端 1 张截图全部符合预期。

## 四、P3 架构与工程（一个月内穿插做，9 项）

### P3-1 · 两个启动入口，线上和本地行为不一致

**这是最容易埋雷的一条。**

| 文件 | 对账频率 | 老数据迁移 | 旧网址兼容 | SPA 兜底 |
|---|---|---|---|---|
| `[代码] main.ts`（48 行） | **距上次满 20 小时才跑** | 无 | 无 | 无 |
| `[代码] main-zeabur.ts`（85 行） | **每小时无条件跑** | 有 | 有 | 有 |
| `[代码] Dockerfile:31` | `CMD ["npx", "tsx", "apps/server/src/main-zeabur.ts"]` | ✅ | ✅ | ✅ |

**后果**：
- 本地开发用 `main.ts`，**测不出老数据迁移的问题**（因为本地根本不跑迁移）。
- 线上用 `main-zeabur.ts`，**对账频率高 24 倍**。对账要扫全部会员 + 全部流水，会员多了会明显卡顿（`members.reconcile()` 是同步 SQLite 操作，Node 单线程会阻塞）。
- 更严重：`main-zeabur.ts` 的 `reconcileNightly` **没有 try/catch**（`main.ts` 也没有）。对账抛异常 → `setInterval` 的回调里抛出 → **`uncaughtException` → 进程退出 → 全店点不了单**，而且这个退出发生在每小时一次的定时器里，可能在营业高峰。

**修法**（三件，按优先级）：
1. **给定时器加 try/catch**（5 分钟，最高优先级）。
2. **合并成一个 `main.ts`**，用环境变量控制差异行为（`LEGACY_DB_PATH` 有值才迁移，`SERVE_STATIC=1` 才有静态，旧网址兼容无条件无害）。**0.5 天**。
3. **对账频率统一**：改成"每 10 分钟检查一次，距上次满 20 小时才真跑"，和 `main.ts` 一致。

### P3-2 · 进程级异常无兜底，无优雅退出

`[实测]` 全项目搜索 `process.on('uncaughtException')`、`unhandledRejection`、`SIGTERM`、`SIGINT` —— **一个都没有**。

**后果**：
- 任何未捕获的 Promise rejection（比如那个没有 await 的 `afterSubmit()`）都可能在某些 Node 版本下导致退出。
- `docker stop` 时直接 SIGKILL（因为不响应 SIGTERM）→ **SQLite 可能留下未刷盘的 WAL**。虽然有 WAL 恢复机制，但 `print_jobs` 里正在重试的打印任务会丢失。

**修法**：
```ts
process.on('unhandledRejection', (e) => console.error('[未处理的 Promise 错误]', e));
process.on('uncaughtException', (e) => { console.error('[未捕获异常]', e); /* 记录后决定是否退出 */ });
process.on('SIGTERM', () => { db.close(); server.close(); process.exit(0); });
```

**0.5 天**（要小心：`uncaughtException` 之后进程状态可能已经不可靠，稳妥做法是"记录 → 优雅关闭 → 由 Docker 重启"）。

### P3-3 · 备份只有 24 小时，误操作一天后就无法回滚

**实测**：

```
backups/ 38 个快照，每个 184320 字节（180 KB），每个 10 分钟一个
snapshot-2026-10-25T11-02-47 ... snapshot-2026-10-25T14-30-48
```

`[代码] apps/server/src/backup.ts:8` — `keep = 144`，10 分钟一次 × 144 = **24 小时**。

**问题**：如果周一发现"上周五把某个价格改错了"，备份已经滚动掉了。**只剩 24 小时，等于没有历史。**

**修法**（分层保留，很标准）：
- 每 10 分钟 × 24 小时（现有，144 个）
- 每小时 × 7 天（168 个）
- 每天 × 30 天（30 个）
- 合计 342 个 × 180 KB ≈ **60 MB**，完全可以接受（数据量大了按比例增长）

**工时**：0.5 天。**另外** `deploy/litestream.yml` 已经写好了（保留 30 天、可回到任意时间点），**只是没启用**——等服务器和对象存储定下来，这个比本地快照强得多。

### P3-4 · 没有 CORS、没有安全响应头、没有限流

`[实测]` 全项目搜索 `cors` / `Access-Control` / `X-Frame-Options` / `Content-Security-Policy` / `rateLimit` —— **全部为空**。

**逐条看危险程度**：

| 缺什么 | 危险程度 | 为什么 |
|---|---|---|
| **限流** | **中高** | 下单接口 `[代码] orders.ts:31` 注释自承"不防重复、不限频率"。恶意或误操作可以刷单。**但**：店在局域网 + 有密码保护，外部攻击面小。**真正的问题是顾客狂点**（弱网下手机会重试）——这个 P0-1 的幂等键能解决 90%。 |
| **安全头** | **中** | 没有 `X-Frame-Options`，理论上可以被 iframe 嵌套做点击劫持。店在小红书/WhatsApp 分享链接，风险不高但零成本能加。 |
| **CORS** | **低** | 前后端同源部署（`SERVE_STATIC=1`），本来就不需要 CORS。**不加是对的**，加了反而危险。 |

**修法**：
- 加 `X-Frame-Options: SAMEORIGIN`、`X-Content-Type-Options: nosniff`、`Referrer-Policy` —— 三行中间件。
- **SSE token 走 query 是个真问题**：`[代码] apps/admin/src/api.ts:79` `new EventSource('/api/admin/stream?token=...')`。如果前面有 Nginx / Cloudflare，**token 会落进访问日志**。修法：改成 "短时一次性 ticket"（`POST /api/admin/stream-ticket` 拿一个 60 秒有效的 ticket，用它建 EventSource）。**0.5 天**。
- 限流：**可以不做**（局域网场景 + P0-1 修完后，收益不大）。

**工时**：安全头 10 分钟，SSE ticket 0.5 天。

## 六、明确**不**建议做的（5 项，省你的钱和时间）

审查过程中我考虑过这些，核对后认为**现在做是浪费**：

| 项 | 为什么不做 |
|---|---|
| **库存进销存** | 现在是"在售 / 今日售罄 / 下架"三态。加真实库存数量意味着每次下单要扣减、每天要盘点、还要处理"卖了 3 份但实际只剩 1 份"。**小店根本管不住这个数**，反而制造矛盾。三态设计是对的。 |
| **虚拟列表 / 前端性能优化** | JS 81.93 kB gzip，104 道菜全部渲染无压力。`[实测]` 375×667 截图正常。现在做虚拟列表是"为了优化而优化"。 |
| **引入 Redis / 消息队列** | 单店、单进程、SQLite + Node 单线程，天然串行。加 Redis 只会多一个会挂的东西。 |
| **换成 PostgreSQL** | SQLite 的 WAL 模式 + 触发器在这套场景下**比 Postgres 更合适**：零运维、单文件备份、触发器保证不变量。除非开到 5 家店，否则不该换。 |
| **CORS / 认证框架（JWT / OAuth）** | 前后端同源、单店、单密码，现有方案（token 哈希入库 + timingSafeEqual + 锁定）**已经够了**。 |

## 十一、修复过程中新发现的问题（施工时挖出来的）

方案书是在纸面上审出来的。真正动手改的时候，又挖出 18 个**纸面审不出来、但现场会直接出事**的问题，都已修复并加了回归测试。

| # | 问题 | 有多严重 | 怎么发现的 | 怎么修的 |
|---|---|---|---|---|
| R1 | **顾客永远看不到自己的订单** | **P0**：客人下完单回头看「我的订单」永远是「还没有订单」，取餐页也找不到单，只能靠记着取餐号 | 实测截图时发现顾客端订单列表一直是空的，查库发现 `orders.device_id` 存的是**购物车 id**，而查询用的是**手机设备号**，两个值永远不相等 | `SubmitOrderInput` 增加 `deviceId`，前端下单时带上；服务端校验格式后使用，没带才回退购物车 id（兼容已装在客人手机上的老页面）。4 个回归用例 |
| R2 | **错误上报接口自己一直是 500** | **P0（静默）**：整套错误监控形同虚设，一条错误也收不到，而且因为前端是 fire-and-forget，现场没人会发现 | 造了 4 条测试错误，页面上显示 0 条，查库是空表，直接打接口看到 500 | 去重 SQL 里 `ifnull(source, "")` 用了**双引号**，SQLite 把它当列名而不是字符串，整句 prepare 抛错。改成 `source IS ?` / `lineno IS ?`（NULL 也不能用 `=` 比）。8 个回归用例 |
| R3 | **跨班次退款的钱在两边的账上都消失** | 高：比如 10-17 卖了 RM 19.90，10-18 客人投诉全额退。全额退款会自动把单置为「已取消」，而报表按「已取消不计营收」过滤，结果**两天的报表都是 0**，柜台明明退出去了钱 | 写日结单测试时，「今天卖、明天退」这个用例一直算不过 | ① 退款总额改为按**退款发生时刻**归属（谁掏的钱算谁的班）；② 退过款的取消单仍计入营收，让「下单 +19.90 / 退款 −19.90」在同一张纸上抵消；③ 跨班退款在付款方式明细里也补一行，保证明细合计 = 总额。1 个专门用例，含"明细必须对得上总额"的断言 |

**一处误判（记下来防止再犯）**

扫菜品管理时，我一度以为「今日售罄 / 下架 / 改价」三个操作全部失效——界面看着没变。连着排查两轮，最后发现**是我的测量方法错了**：我用「三个按钮的文字顺序」判断哪个是选中态，但文字顺序永远不变，真正在变的是 `aria-pressed`。改用它判断后，三个状态切换和改价全部正常（接口 200，刷新后仍持久化）。

教训：**测「选中态」不要读文字，要读 `aria-pressed` / `data-state` / `checked`。** 这也是我上一轮把 R11 记成「Playwright 怪毛病」的同一个毛病——用了一个不可靠的观测口径，然后把观测不到当成「不存在」。

### 为什么 R11 能活这么久

它不在方案书的 42 项里，也不是哪次改动引入的——它从一开始就在。绕开它的路径恰好有两条，而开发时两条都走了：

1. **服务端测试**直接 `POST /api/cart/update`，从来不经前端这个函数（288 个用例全绿）
2. **实拍脚本**也因为点不动加号，中途改成「用接口备菜」，把这个现象当成了「Playwright 的怪毛病」记进了已知限制

真正把它暴露出来的是这次换了个思路：**不写断言，只让真实浏览器从头点一遍，看它到底发生了什么。** 之前几轮做的是「验证我认为对的东西」，这次做的是「看用户会经历什么」，差别就在这里。

教训写进流程：**每加一个功能，至少留一条只用 UI、不碰接口的端到端脚本。** 接口测试保证服务端对，UI 测试保证顾客真的能下单，两者不能互相替代。

另外一个**判断被推翻**：

- 方案书里 P1-7「跨午夜营业判定可能卡住」——**查证后不存在**。`menu.ts` 的 `withinHours()` 本来就有跨夜分支，`dishes-store.test.ts` 里也有「跨夜营业 17:00–02:00」的测试。已从修复清单剔除，没有改代码。

### 那个「Playwright 的怪毛病」，其实就是 R11

之前几轮我一直把「点单页的加号在自动化里点不生效」记成「Playwright 的怪毛病，与业务无关」，并在实拍脚本里绕开它。**绕错了。**

查清之后的事实：原生 `pointerdown / mousedown / pointerup / mouseup / click` 全部到达按钮，React 的 `__reactProps.onClick` 存在、手动调也能跑——**事件系统一直好的**。是 `onClick` 里面的 `cart.change()` 在购物车没有这道菜时直接返回了。真人手点同样点不动，我当时没验证「真人手点正常」这个说法，只是想当然。

所以那条「已知限制」本身就是误判。已经从 `系统架构一页纸.md` 的已知限制表里删掉，换成 R11 的修复记录。

**三条可以复用的判据**：

- 「只有自动化工具不行、真人可以」这个结论，必须真拿真人设备验一次再说，否则它常常是在为一个真 bug 找台阶
- 查前端点击问题时，先分清「事件有没有到」和「handler 做了什么」——前者看原生监听器，后者直接把 `__reactProps.onClick` 拿出来调一遍，两步就能把范围砍一半
- 自动化脚本里绕开某个操作 = 这个操作从此没有任何测试覆盖，比不做测试更危险
