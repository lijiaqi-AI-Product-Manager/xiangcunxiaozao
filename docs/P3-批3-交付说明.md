## 一、数据看板（第③项）

老板端左侧「数据看板」原来是占位文字，现在是能用的页面（截图 `docs/screenshots/p3-batch3/老板-数据看板-今天.png`）：

- **三个大数字**：实收营收（下面一行写「下单 − 退款」）、有效订单（附已取消单数、客单价）、储值净变动（附此刻全店储值余额）。
- **按付款方式**：每种方式的单数、下单、退款、实收，最后一行合计。
- **储值变动**：充值、消费、退款、调整、迁移导入逐项，最后是净变动和流水笔数。
- **近 7 天**：每天的有效订单、实收、储值净变动，点哪天就看哪天；顶部可以「前一天 / 后一天 / 回到今天」。
- **「这些数怎么算的」**：页面底部折叠说明，四条口径写给老板看。
- 按 29号 / 31号的克制原则：只有表格和大数字，没有图表库。

### 口径（打个比方：看板是对着三本账现算的计算器，不是另记的第四本账）

| 数 | 怎么算 |
|---|---|
| 营业日 | 门店时区的日历日，和取餐号每天归零、售罄第二天恢复是同一条线 |
| 有效订单 | 当天下单、没有取消的单（店员取消和「全部菜品已退款」自动取消都不算） |
| 实收营收 | 有效订单的下单金额 − 这些订单上的按菜品行退款 |
| 按付款方式 | 混合支付的单：储值部分记在储值，其余记在另一种方式，两边各算一单；退款按「储值先退」分到两边 |
| 储值净变动 | 当天全部储值流水的合计；「此刻全店储值余额」不随所选日期变 |

每个数都由服务器从订单、退款、储值流水三本账当场算出来，**不另存统计表**，所以看板永远不会和账本对不上。

## 二、我自己发现的问题（5 条）

1. **老板端长页面整页截图下半截是白的**：深色背景是「固定在屏幕上」的渐变，真浏览器滚动时没问题，但整页截图只画了一屏高。已加一层纯深色底兜住，截图和长页面都正常（会员管理等长页面以后截图也受益）。
2. **看板的端到端测试不能单独跑**：它要用前面几批测试在同一个测试库里下过的单。整套一起跑没问题；单独跑会因为「今天 0 单」失败，这是有意的，已在测试开头写明。
3. **营业日分界还是午夜**：如果高斯以后定「凌晨 4 点才算换天」（宵夜店常见），取餐号归零、售罄恢复、看板三处要一起改。现在这三处共用同一个营业日函数，改一处就三处一起变；分界时间仍是待高斯提供的事项。
4. **「客单价」用实收除以有效订单**：退过款的单拉低客单价。这是我定的口径，如果老板习惯按下单金额算，改一行就行，请确认。
5. **为了让新接口生效，重启了开发用的服务器**：之前是我手动开的，现在改由预览工具托管。没有影响任何数据。

## 三、第④项方案（等你批准下载）

第④项有两件事：书法字体自托管、图片自动压缩到 300KB 以内（上传侧 + 出图侧）。

### 1. 书法字体自托管（推荐方案：按用到的字裁剪）

| 步骤 | 说明 |
|---|---|
| ① 下载字体原文件 | 马善政体（Ma Shan Zheng）官方源：Google Fonts 在 GitHub 上的开源仓库 `google/fonts` 里的 `ofl/mashanzheng/MaShanZheng-Regular.ttf`，许可证 SIL OFL 1.1（允许自托管和裁剪）。大小约几 MB，以实际为准。 |
| ② 装一个裁剪工具 | npm 开发依赖 `subset-font`（只在生成字体时用，不进顾客页面） |
| ③ 只留用到的字 | 书法只用在仪式位（35号 Q2）：菜名、印章、水印、店名。脚本从品牌配置和菜单数据里收集这些字，裁出一个只含这几百个字的小字体，预计一两百 KB，放进 `brands/` 下 |
| ④ 去掉谷歌字体链接 | 顾客端不再依赖谷歌，马来西亚 / 中国网络下都能稳定显示 |
| ⑤ 加一道检查 | 菜单以后加了新菜、出现新字，数据校验会提示「有字不在书法字体里，请重新生成」 |

### 2. 图片压缩到 300KB 以内

| 位置 | 做法 | 要不要下载 |
|---|---|---|
| 上传侧（老板端上传图片） | 浏览器里先缩到最长边 1200 像素、转成 WebP 再上传，超过 300KB 自动降质量重压；服务器照旧做四项检查 | **不用下载**，浏览器自带能力 |
| 出图侧（生图管线批量出的图） | 一个脚本把 `assets/` 里的图批量压到 300KB 以内，压不下来的列清单 | 需要装图片处理库 `sharp`（npm 开发依赖） |

**需要你批准的下载**：字体原文件 1 个（来源如上）、npm 开发依赖 `subset-font` 和 `sharp`。批准后我按上面的顺序做，一批交付，附裁剪前后的字体大小和截图对比。
